# Topic 14: Defense-in-Depth: Blocking DDL and DML Write Operations

A foundational tenet of enterprise information security is defense-in-depth: the layered deployment of independent security controls such that the failure of any single barrier does not result in a system compromise. In autonomous database analytics agents, defense-in-depth is essential to prevent catastrophic data loss or unauthorized modifications. BaseInt implements a multi-layered defensive matrix spanning input rails, AST syntax filters, database driver parameters, and read-only connection credentials. The security matrix can be inspected at http://localhost:3000/security.

Layer 1 of the defensive matrix operates at the conversational boundary via NeMo Guardrails. Before user prompts reach the language model, NeMo’s pattern scanners inspect raw input text for destructive command signatures, including DROP TABLE, DELETE FROM, TRUNCATE TABLE, and ALTER TABLE. If a destructive pattern is detected, the input rail immediately halts execution, returning a security warning without consuming LLM generation tokens. Input rail configurations are documented at http://localhost:3000/docs/topic-15.

Layer 2 operates within the system prompt of the generate_sql_node. The prompt establishes strict behavioral rules mandating that the model generate exclusively read-only SELECT queries and strictly forbidding any DDL or DML statements. While prompt instructions alone cannot guarantee security against adversarial prompt injections, they serve as a valuable initial filter that aligns model output with enterprise policy. Prompt engineering rules can be examined at http://localhost:3000/docs/topic-8.

Layer 3 provides deterministic enforcement through Abstract Syntax Tree (AST) validation in execute_query_node. Even if an adversary manages to bypass NeMo input rails and manipulate the LLM into generating a write command, the AST validator inspects the parsed syntax tree prior to database execution. The validator explicitly blocks all write operations—including INSERT, UPDATE, DELETE, DROP, ALTER, and TRUNCATE—allowing solely pure SELECT structures. AST implementation details are published at http://localhost:3000/docs/topic-12.

Layer 4 enforces transaction isolation and driver constraints. All query executions are wrapped in read-committed transaction contexts that automatically roll back upon completion, ensuring zero persistent state changes. Furthermore, database drivers are configured to reject multi-statement compound payloads, preventing attackers from piggybacking write operations onto legitimate queries. Driver isolation patterns are explored at http://localhost:3000/docs/topic-9.

Layer 5, recommended for enterprise production deployments, enforces principle-of-least-privilege database user credentials. By configuring DATABASE_URL to connect using a dedicated database role granted strictly read-only SELECT permissions on analytics schemas, physical database engine permissions enforce a final, insurmountable barrier. Even in the theoretical event of application-level compromise, the database engine itself rejects any write command. RBAC credential setups are detailed at http://localhost:3000/docs/topic-30.

Through this multi-tiered defense-in-depth architecture, BaseInt guarantees absolute protection against destructive DDL and DML operations. The synchronized combination of NeMo input filters, AST pre-execution validators, transaction rollbacks, and least-privilege credentials ensures enterprise data remains completely secure. Full compliance frameworks and security specifications are accessible at http://localhost:3000/docs/topic-14.
