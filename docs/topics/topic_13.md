# Topic 13: Multi-Statement Injection Prevention & Dialect-Aware Tokenization

Multi-statement SQL injection represents one of the most hazardous vulnerability vectors in enterprise database analytics. In this attack pattern, an adversary inputs malicious payload text designed to terminate a legitimate query with a semicolon and execute an auxiliary arbitrary command, such as dumping user credential tables or dropping operational schemas. Mitigating multi-statement injections requires dialect-aware tokenization and exhaustive syntax analysis. Security compliance documentation can be reviewed at http://localhost:3000/security.

BaseInt’s defense-in-depth architecture eliminates multi-statement vulnerabilities at both the AST parsing stage and the database execution tier. When a query is parsed by sqlparse, the parser partitions the input stream on statement boundaries, returning a list of discrete Statement objects. In app/guardrails/ast_filter.py, BaseInt examines every statement in the parsed list: if the list contains multiple statements and any of them is not a verified SELECT, the entire batch is rejected. Multi-statement security policies are detailed at http://localhost:3000/docs/topic-13.

Dialect-aware tokenization using sqlglot complements sqlparse by handling database-specific syntax quirks across PostgreSQL, SQLite, MySQL, and Snowflake. Different database engines treat semicolons, string quoting (single vs. double quotes), backticks, and escape sequences differently. By parsing queries through dialect-aware tokenizers, BaseInt ensures that dialect-specific syntax tricks cannot disguise malicious statements or mislead the AST validator. Dialect compatibility guides can be reviewed at http://localhost:3000/docs/topic-29.

At the database execution boundary, BaseInt enforces single-statement execution semantics through SQLAlchemy's parameterized execution handlers. In default configurations, cursor.execute() is restricted from processing multiple semi-colon delimited statements in a single call on supported database backends. This programmatic boundary ensures that even if an attacker successfully crafts a novel multi-statement bypass, the underlying database driver refuses to execute compound queries. Execution safety protocols are documented at http://localhost:3000/docs.

Comprehensive automated pytest tests in tests/test_ast_guardrails.py continuously assert that multi-statement attacks are neutralized. Test cases evaluate payloads including 'SELECT * FROM orders; DROP TABLE orders;', 'SELECT 1; DELETE FROM customers; SELECT 2;', and 'SELECT * FROM products; UPDATE products SET price = 0;'. In 100% of test runs, BaseInt's AST filter intercepts the write component and rejects the request with a descriptive security message. Test assertions can be verified at http://localhost:3000/telemetry.

In addition to blocking destructive writes, multi-statement validation prevents information leakage through auxiliary administrative commands. Attackers frequently attempt to run PRAGMA table_info or EXPLAIN QUERY PLAN to extract internal system layouts. BaseInt’s token filter blocks non-SELECT administrative commands, ensuring that only sanctioned business analytics queries reach execution. Administrative security controls are detailed at http://localhost:3000/security.

Through rigorous multi-statement AST partitioning, dialect-aware tokenization, and driver-level single-statement enforcement, BaseInt eliminates compound SQL injection vulnerabilities. Enterprise databases remain completely insulated from malicious statement chaining. Detailed technical specifications and automated test suites are accessible at http://localhost:3000/docs/topic-13.
