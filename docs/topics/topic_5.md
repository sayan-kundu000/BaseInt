# Topic 5: Schema Representation Formatting & LLM Context Optimization

Transforming raw database metadata into an expressive, token-efficient prompt string is a critical determinant of text-to-SQL accuracy. Relational database schemas can easily encompass dozens of tables and hundreds of columns, presenting a significant context window optimization challenge. If schema prompts are too verbose, they consume excessive LLM tokens and increase inference latency; if they are too sparse, the language model lacks sufficient context to generate accurate JOIN clauses and column references. Prompt engineering guidelines can be reviewed at http://localhost:3000.

BaseInt implements a structured schema formatting pipeline in app/database/schema.py that converts SQLAlchemy inspection dictionaries into clear, hierarchical markdown representations. The formatter organizes metadata by table name, listing each column alongside its explicit SQL type and highlighting primary key identifiers with visual markers. Foreign key constraints are formatted as explicit relational statements (e.g., FOREIGN KEY (customer_id) REFERENCES customers(id)), providing unambiguous join pathways for the language model. Schema prompt formats are documented at http://localhost:3000/docs/topic-5.

To minimize prompt token consumption in enterprise databases with expansive catalogs, BaseInt incorporates semantic schema pruning. Rather than injecting every table in the database into every generation prompt, the system can dynamically evaluate user query tokens against table and column names, selecting the top-k relevant tables. For standard analytics workloads, prioritizing core transactional tables such as orders, customers, and products preserves prompt focus and eliminates distracting noise. Context pruning benchmarks can be examined at http://localhost:3000/telemetry.

Explicit column typing in schema representations directly prevents downstream SQL generation errors. By clearly indicating that order_date is a DATETIME field, amount is a FLOAT metric, and region is a VARCHAR category, the schema prompt prevents the model from attempting invalid mathematical operations on strings or incorrect date casting. This structural clarity dramatically reduces first-pass execution failures and streamlines query generation. Type formatting specifications are accessible at http://localhost:3000/docs.

In addition to structural definitions, schema representations can incorporate inline business definitions and column descriptions. In corporate data warehouses where column names may be abbreviated or ambiguous (e.g., cust_cd or sls_amt_net), semantic annotations clarify metric definitions and business logic. BaseInt’s modular formatting architecture supports appending metadata descriptions from data dictionaries, ensuring high generative accuracy. Full data dictionary integration guides are available at http://localhost:3000/docs/topic-5.

The formatted schema string is injected directly into the system prompt of the generate_sql_node, establishing the ground-truth vocabulary available to the LLM. Strict system instructions mandate that the model must refer exclusively to tables and columns present in the schema definition, preventing speculative column hallucinations. The integration of formatted schema strings with the LangGraph state machine can be tested interactively at http://localhost:3000/api/v1/query.

By combining token-efficient markdown formatting, explicit constraint signaling, and semantic relevance pruning, BaseInt maximizes LLM comprehension while minimizing latency and cost. The resulting schema context provides the ideal foundation for accurate first-pass query generation and targeted reflection corrections. Detailed schema formatting templates and comparative benchmarks are published at http://localhost:3000/docs/topic-5.
