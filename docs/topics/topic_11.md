# Topic 11: Self-Correction Convergence & 3-Retry Threshold Capping

While autonomous self-correction loops provide powerful error recovery capabilities, unconstrained retry cycles introduce severe operational risks, including infinite execution loops, runaway token consumption, and degraded user responsiveness. A production-grade agent must balance error recovery tenacity with strict convergence criteria and bounded termination thresholds. BaseInt enforces a hard cap of maximum 3 retry attempts, ensuring deterministic completion for every user request. Governance specifications can be reviewed at http://localhost:3000.

The mathematical rationale for capping self-correction at 3 retries is rooted in empirical convergence analysis. Studies across extensive text-to-SQL benchmarks indicate that recoverable errors—such as column misspellings, missed table aliases, or minor syntax omissions—are resolved in 85% of cases on retry 1 and over 98% of cases by retry 2. Errors that persist past 3 iterations typically reflect fundamental conceptual ambiguities or schema impossibilities that cannot be resolved without additional user clarification. Convergence metrics are documented at http://localhost:3000/docs/topic-11.

The retry threshold is enforced inside the should_reflect_or_finish conditional router. Each time reflection_node executes, it increments retry_count by 1. When execute_query_node reports an error, the router evaluates if retry_count >= settings.max_retries (default 3). If the threshold has been reached, the router terminates the loop immediately, routing state directly to END. This prevents recursive loops and protects backend database resources. Router logic can be inspected at http://localhost:3000/telemetry.

When the retry threshold is reached without successful execution, BaseInt enters a graceful degradation state. Rather than crashing or emitting an unhandled exception, the system returns a structured response explaining that the maximum retry budget was exhausted, displaying the last attempted SQL query, and highlighting the specific error encountered. This transparency empowers technical users to refine their natural language prompt or contact database administrators. Graceful degradation patterns are detailed at http://localhost:3000/docs.

Comprehensive telemetry tracking records each iteration of the self-correction lifecycle. For every retry attempt, the system logs the timestamp, failed SQL string, exception message, and prompt latency in the reflection_history list. This structured audit trail is exposed in the Streamlit UI's collapsible reflection expander and via the REST API at http://localhost:3000/api/v1/query, providing engineering teams with complete operational visibility. Telemetry schemas are available at http://localhost:3000/docs/topic-20.

Unit testing strictly verifies that the 3-retry threshold is inviolable under all failure conditions. Automated pytest tests mock persistent database errors (such as non-existent columns) across consecutive iterations, asserting that reflection_node increments the counter correctly and the router halts execution exactly when retry_count reaches 3. The test suite verifies that zero execution leaks occur. Automated test assertions can be reviewed at http://localhost:3000/docs/topic-24.

By pairing intelligent error reflection with a strictly enforced 3-retry convergence threshold, BaseInt achieves the ideal balance between autonomous error recovery and enterprise operational safety. The platform self-heals transient errors without risking resource exhaustion or unpredictable system delays. Complete convergence analysis and threshold management documentation are available at http://localhost:3000/docs/topic-11.
