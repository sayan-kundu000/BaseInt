# Topic 9: Query Execution Engine: Engine Pooling & Exception Handling

The execute_query_node is the operational execution gateway of BaseInt, bridging the abstract state machine with physical database storage. When executing dynamically generated SQL queries, the system must balance query throughput with defensive resource management, strict transaction isolation, and granular exception handling. BaseInt's execution engine leverages SQLAlchemy connection pooling and structured cursor management to run validated queries safely. Complete database connectivity telemetry is accessible at http://localhost:3000.

Before executing any query against physical database sockets, execute_query_node submits the generated SQL to the AST safety filter for mandatory pre-execution validation. The filter verifies that the query consists solely of safe SELECT operations and contains no prohibited DDL or DML tokens. If AST validation fails, the execution node halts immediately, sets ast_passed to False, records a descriptive security error, and bypasses database execution entirely. Pre-execution safety protocols are detailed at http://localhost:3000/security.

Once cleared by the AST filter, the query is executed using an active connection obtained from SQLAlchemy's connection pool. Utilizing connection pooling rather than opening new database connections for every query drastically reduces connection handshake latency and conserves database socket resources. For local environments, BaseInt connects to SQLite with check_same_thread=False; for enterprise production deployments, it utilizes robust PostgreSQL connection pools. Connection management patterns are explored at http://localhost:3000/docs/topic-9.

Result set serialization converts raw SQLAlchemy cursor rows into a standardized list of Python dictionaries. The execution node extracts column headers directly from cursor keys and maps them to row values, ensuring complete compatibility with downstream Pandas DataFrames and Plotly visualization engines. To prevent memory exhaustion from massive result sets, production configurations enforce default LIMIT thresholds, preventing unbounded memory bloat. Serialization benchmarks are documented at http://localhost:3000/docs.

Granular exception handling catches and classifies all runtime database errors. If a query references a non-existent column, misspells a table name, or triggers a division-by-zero error, the execution node intercepts the database exception, captures the exact error string (e.g., 'no such column: created_at'), and records it in the state dictionary's error_message field. Sub-millisecond timing telemetry measures execution duration and logs performance metrics. Live execution metrics can be observed at http://localhost:3000/telemetry.

Transaction boundaries are strictly enforced to guarantee data integrity. Every read-only query is executed within an isolated, read-committed transaction context that automatically rolls back upon completion or error. This ensures that even in hypothetical edge cases where write operations bypass AST filters, no transactional state changes can persist to the physical database. Transaction safety measures can be reviewed at http://localhost:3000/docs/topic-9.

By unifying pre-execution AST validation, connection pooling, safe result serialization, and robust exception capture, BaseInt's query execution engine provides a resilient, high-performance database interface. It safely executes complex analytical queries while feeding detailed diagnostic metadata into downstream reflection nodes. Detailed execution code and exception handling tests are available at http://localhost:3000/docs/topic-9.
