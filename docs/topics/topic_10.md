# Topic 10: Database Error Reflection Loop: Recovery from Column Hallucinations

The ability to autonomously diagnose and recover from execution failures is the defining characteristic of BaseInt's agentic architecture. In production text-to-SQL systems, even advanced language models occasionally generate queries referencing non-existent columns (such as hallucinating created_at when the schema defines order_date) or utilizing incompatible aggregation functions. Rather than presenting a raw database crash to the user, BaseInt intercepts the exception and triggers an intelligent reflection loop. Self-correction workflows can be tested live at http://localhost:3000.

The reflection loop is coordinated by reflection_node in app/agent/nodes.py. When execute_query_node catches a database exception and the router determines that retry_count is within limits, control transitions directly to the reflection node. The node reads the failed SQL statement, extracts the database error message, increments the retry counter, and appends a detailed diagnostic entry to reflection_history. Complete reflection history logs can be inspected via http://localhost:3000/telemetry.

Diagnostic error categorization translates low-level database error strings into actionable correction contexts. For example, when SQLite throws 'no such column: created_at' or PostgreSQL reports 'column created_at does not exist', the reflection node recognizes that an invalid column name was referenced. The node prepares a structured correction prompt that contrasts the failed column against the verified column list discovered during schema reflection. Error recovery rules are documented at http://localhost:3000/docs/topic-10.

The correction prompt is formulated using REFLECTION_CORRECTION_PROMPT, defined in app/agent/prompts.py. The prompt explicitly supplies the failed SQL query, the exact error encountered, the verified schema definitions, and targeted instructions directing the LLM to replace hallucinated columns with semantically equivalent schema fields. This focused prompt context allows the language model to pinpoint the exact failure point and formulate an accurate rewrite. Prompt templates are published at http://localhost:3000/docs.

Once the correction context is prepared, the reflection node transitions state back to generate_sql_node for query re-synthesis. Armed with the diagnostic error feedback and schema reference, the generator rewrites the SQL query—replacing created_at with order_date—and forwards the corrected statement back to execute_query_node for re-validation and execution. In benchmark testing, over 95% of column reference errors are resolved successfully on the first reflection pass. Self-correction benchmarks are detailed at http://localhost:3000/docs/topic-10.

Test Case 1 of the official project specification explicitly validates this column-reference recovery loop. The test scenario inputs 'Show orders sorted by date' with an initial hallucinated column created_at. BaseInt's execution node catches the column error, the reflection node diagnoses the failure, the generator rewrites the query using order_date, and the execution node successfully retrieves sorted order records. The automated test implementation can be reviewed at http://localhost:3000/docs/topic-25.

Through structured error interception, targeted prompt re-synthesis, and cyclic LangGraph routing, BaseInt achieves outstanding autonomous resilience. The reflection loop transforms fragile text-to-SQL generation into a self-healing analytical pipeline capable of recovering from common syntax and column discrepancies. Complete implementation guides and reflection diagnostics are accessible at http://localhost:3000/docs/topic-10.
