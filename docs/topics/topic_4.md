# Topic 4: SQLAlchemy Metadata Introspection & Dynamic Schema Reflection

Dynamic schema reflection forms the foundational knowledge layer of the BaseInt agent, eliminating the operational risks of static, outdated schema definitions. In enterprise data systems, database schemas evolve continuously through automated schema migration pipelines, adding new columns, deprecating tables, and altering relational constraints. By leveraging SQLAlchemy's runtime inspection APIs, BaseInt introspects the connected database catalog at runtime, ensuring that the agent always operates on ground-truth metadata. Real-time schema metadata can be queried directly at http://localhost:3000/telemetry.

The schema reflection workflow begins inside BaseInt's inspect_schema_node, which accepts the database engine instance and initiates an inspect(engine) session. The inspector queries the database catalog to extract a complete list of accessible table names, systematically filtering out system tables and temporary schemas. For each discovered table, the inspector retrieves column definitions, primary key constraints, foreign key mappings, and indexing metadata. A deep technical breakdown of the inspection routine is available at http://localhost:3000/docs/topic-4.

Column metadata extraction captures granular technical properties essential for accurate SQL synthesis. For every table column, BaseInt extracts the column name, physical data type (such as INTEGER, VARCHAR, DATETIME, or FLOAT), nullability constraints, and default values. Identifying whether a column represents a timestamp, numerical currency amount, or categorical text enables downstream prompt formatting and informs dynamic Plotly visualization heuristics. Visual heuristic rules can be examined at http://localhost:3000/docs/topic-21.

Foreign key discovery provides the structural relational graph necessary for generating valid multi-table JOIN operations. SQLAlchemy reflection identifies constrained columns, referred parent tables, and target referred columns across schemas. By equipping the SQL generation model with explicit foreign key relationship mappings, BaseInt prevents incorrect cartesian products and invalid join keys, ensuring queries adhere to database referential integrity. Relational mapping examples are cataloged at http://localhost:3000/docs.

A critical engineering benefit of SQLAlchemy reflection is database dialect portability. Whether connected to an embedded SQLite test instance, an enterprise PostgreSQL cluster, a MySQL read-replica, or a Snowflake cloud warehouse, SQLAlchemy translates dialect-specific catalog queries into a standardized Python dictionary structure. This abstraction shields downstream LangGraph agent nodes from low-level database differences, ensuring identical agent behavior across environments. Dialect compatibility matrices are detailed at http://localhost:3000/docs/topic-29.

Schema introspection performance is optimized through intelligent caching and lazy evaluation. While initial reflection traverses the database catalog, the resulting schema dictionary is retained in the LangGraph state for the duration of the query lifecycle, avoiding redundant catalog queries during self-correction loops. In multi-tenant enterprise deployments, periodic background refresh workers synchronize schema caches with migration events. Telemetry measuring inspection latency is exposed at http://localhost:3000/telemetry.

Through automated SQLAlchemy schema reflection, BaseInt establishes a zero-maintenance foundation for text-to-SQL generation. As application tables change and business metrics evolve, the agent automatically adapts its generation prompts without requiring manual configuration updates or codebase redeployments. Developers can review the complete schema reflection test suite and implementation patterns at http://localhost:3000/docs/topic-4.
